alpine_postgres_setup
#

recipe_alpine_postgres.ts view source

(options: AlpinePostgresSetupOptions): ScriptCommands import {alpine_postgres_setup} from '@fuzdev/zap/recipe_alpine_postgres.js';

Build the postgres-cluster-init script's check/run for Alpine.

run initializes the data cluster via the OpenRC setup action (Alpine's apk install does not, unlike Debian's apt), then closes the trust rules that action's initdb writes into the new pg_hba.conf: local lines become peer (the OS account named like the role) and host lines scram-sha-256 (a password), so no account on the machine connects as any role, postgres included, without a credential. Debian's cluster starts with those methods. The rewrite runs as postgres, which owns the file and its directory (sed -i stages its copy there), and the script fails if a trust rule is left. A server already running is told to reload (rc-service --ifstarted), so the new rules are in force.

check passes once the cluster's PG_VERSION marker exists and its pg_hba.conf holds no trust rule. So a run that failed after setup is retried on the next apply, and that run skips setup (the cluster is there) and goes straight to the rewrite; a cluster set up before this recipe, trust rules and all, is rewritten the same way.

A client that relied on a trust rule stops connecting. Every trust line in the file is rewritten, not only initdb's: a service that reaches PostgreSQL over TCP with no password is refused once the rewrite is in force, and one on the socket is admitted only as the OS account named like its role. Move such a client to the socket as its own account (fuz_app_env_base's DATABASE_URL), or give it a password, before this runs on an existing cluster. Sequence it before the postgresql service (the setup action requires the server stopped) and before any zap.database.

the script check/run pair.

CertbotDnsPreflightOptions
#

recipe_certbot.ts view source

CertbotDnsPreflightOptions import type {CertbotDnsPreflightOptions} from '@fuzdev/zap/recipe_certbot.js';

The DNS preflight's option, shared by every certbot script that leads to a CA request.

expected_addresses

The IP addresses every name the certificate covers must resolve to, on the target. Before the script changes anything, the target resolves each name with getent ahosts and getent hosts — through its own resolver, so /etc/hosts first — and refuses when a name doesn't resolve, when no address can be read, or when any A/AAAA address either prints is outside this set: Let's Encrypt validates whichever address it picks, so an undeclared AAAA would fail the validation. The two lookups together see every A and AAAA but in one case: on a musl host (Alpine) with IPv6 disabled, ahosts drops the AAAA records and hosts prints only the first, so a name with several AAAA, the first of them declared, passes unseen.

The guard reads the target's resolver, not the CA's. An /etc/hosts line, a split-horizon answer, or a cached one can pass while public DNS doesn't point at the host yet, or refuse while it does. A name /etc/hosts maps to a loopback address refuses, the safe direction. That includes the 127.0.1.1 <name> line a Debian install writes for the host's own name, when that name is the domain: remove the line, or give the host a name that isn't the domain (a tool that manages /etc/hosts may write the line back).

Each value is an IP literal, or a reference resolving to one at apply time; the target checks it and refuses anything else (a host name, say), asking for this option. An IPv6 address is compared as text, lowercased, so write it as getent prints it (the compressed form). A reference to the target's host ([zap.env('DEPLOY_HOST')]) serves when that is an IP literal; list the addresses when the host is reached by name or the names also carry an AAAA. Required, and not empty.

type readonly string[]

The capabilities= value, in libcap's IAB text, which supervise-daemon applies: ^cap_x raises cap_x as an ambient capability, !cap_x drops it from the bounding set. Defaults to '^', no ambient capability (a daemon listening on a high port behind nginx needs none); pass '^cap_net_bind_service' for one that binds below 1024. Whatever it names, the recipe appends !cap_… for every other capability (CAPABILITY_NAMES by name, then every higher number up to 63, so one a newer kernel adds is dropped too; the names need a libcap that knows cap_checkpoint_restore), so the bounding set holds only the capabilities the value names without !: a '^' alone leaves it empty. libcap's IAB text has no word for "all", so each is named. Under isolation the command holds none.

type string

umask=, which supervise-daemon sets for the daemon (--umask): four octal digits. Defaults to '0077', as the systemd unit does, so what the service creates is its own; pass '0022' (or '0027' for a group) when another account reads what it writes, such as nginx serving a store through X-Accel-Redirect.

type string

type string[]

log_file?

Combined stdout+stderr log path (output_log/error_log). Defaults to /var/log/<name>/<name>.log. supervise-daemon opens this as command_user (after the privilege drop), so for a non-root service the path's directory must be writable by that user. The recipe handles this: it creates and chowns log_file's parent directory to the service user in a start_pre() checkpath hook (which runs as root, before the privilege drop), so the default works for a non-root service out of the box with no external directory resource. Because the parent is chowned to the service user, it must be the service's own: at or under a directory that sits directly under /var/log, /var/lib, /srv, /opt or /run and is named name or user, alone or followed by one of _, -, . (/var/log/<name>/server.log, /srv/<user>/logs/server.log), and env_file must not sit inside it, nor may command or, under isolation, the bwrap binary, which the service user could otherwise replace. Any other path is refused at eval.

At start, the hook also refuses (eerror, start_pre fails) a log directory that already exists unless it is a directory, not a symlink, owned by the service user: an absent one is created, and anything else (root's, another daemon's — a name nginx meeting /var/log/nginx) is someone else's, which the hook never re-owns. A root-owned directory is refused too, since the hook didn't make it; chown it to the service user, or remove it, to adopt it. The residual: only the log directory itself is checked, and checkpath follows a symlink in the path's intermediate components, creating through it and chowning where it points; a symlink as the last component it refuses, failing the start. ssh_hardening_verify
#

recipe_ssh.ts view source

(options: SshHardeningOptions): VerifyResource import {ssh_hardening_verify} from '@fuzdev/zap/recipe_ssh.js';

Build the verify payload that re-asserts the hardening in sshd's effective config for the allowed user on every plan, from the options ssh_hardening was given: root login, password auth, keyboard-interactive auth, and X11 forwarding off, AllowUsers the user and no one else, and the tunables at their values. Pass both the same options object.

sshd prints each keyword lowercase with its value, one AllowUsers entry per line and LoginGraceTime in seconds. Each assertion but one matches one whole line, fixed-string (grep -qxF), the expected line one single-quoted word, so a value is matched as text. sshd adds up AllowUsers across every file it reads, so a presence check would miss a user another drop-in allows: that one compares every allowusers line together with the one expected (test "$(…)" = '…').

It reads what sshd would run with, not the drop-in's bytes, so it catches a drop-in that sorts earlier and overrides the hardening, a hand edit, or a config that no longer parses. A failing check shows as a pending change and blocks zap deploy's preflight. Spread it into a zap.verify that depends on the ssh service.

The config is read for a connection, sshd -T -C user=<user>,host=…,addr=…,lport=<ssh_port>, so a Match block that applies to the allowed user (Match User, Match Group, Match All, an address list that holds every client) and re-enables password auth fails the verify; without -C, sshd prints only the global values. The client address is 192.0.2.1, a documentation address, so a Match Address block naming one real network (an office, a VPN) isn't exercised: the other users it could admit are refused by AllowUsers, but the allowed user from that network is not checked. Nor are Match LocalAddress and Match RDomain blocks: the connection names no local address or routing domain.

Variable values substituted for {{key}}, in one pass: a value is never read for placeholders. A string value may be or carry a reference, resolved before it is substituted. TemplateKind
#

schema.ts view source

TemplateKind

type "text" | "hostname" | "port" | "path" | "email" | "env_value"

import type {TemplateKind} from '@fuzdev/zap/schema.js';

The kind of value a template variable renders to, checked on its whole rendered value. Mirrors the Rust TemplateKind.

  • text — any one line: no line break, NUL, or reference delimiter. Every kind keeps this rule. A reference's value is held to it whether or not its variable declares a kind; a value written out is held to it only when its variable declares one.
  • hostname — a DNS host name (RFC 1123): dot-separated labels of ASCII letters, digits, and -, each 1 to 63 bytes, no leading or trailing -, at most 253 bytes, with no trailing dot, no wildcard, and no _.
  • port — a decimal number from 1 to 65535, with no sign or leading zero.
  • path — an absolute path whose names are ASCII letters, digits, ., _, -, +, and @, with no empty, ., or .. name.
  • email — a local part of ASCII letters, digits, ., _, %, +, and - (no leading, trailing, or doubled .), an @, and a hostname.
  • env_value — a value written inside single quotes in an env file: text with no ', which would end the quoting.

None of the hostname, port, path, or email alphabets holds a character a config grammar reads as structure (;, {, }, a quote, a blank), which is what a kind is for: a {{domain}} in an nginx server_name declared hostname can't end the directive.
