recipe_certbot.ts

Recipes for the certbot bootstrap + renewal scripts.

These build the check/run payloads of the certbot script resources a TLS-terminating host declares:

  • certbot_standalone_issue_core — issues the first certificate via certbot certonly --standalone, stopping nginx first to free port 80; the recipe_debian_certbot.ts / recipe_alpine_certbot.ts wrappers ({debian,alpine}_certbot_standalone_issue) pass the service-manager stop command, the one step that differs by distro.
  • certbot_webroot_switch — re-issues once via --webroot to pin the unattended renewal authenticator to webroot (so renewal works while nginx holds port 80), then runs the deploy hook it is given, so the server picks up the re-issued certificate.

Both take extra_domains for the names beside the primary one a cert covers (the www. alias a site redirects), matching the nginx site recipe's redirect_domains.

Both scripts that lead to a request to the CA — the first issuance and the webroot switch — run a DNS preflight before they change anything: each name the certificate covers must resolve, on the target, only to expected_addresses. A name that doesn't resolve, or resolves anywhere else, refuses the script with the reason on stderr, so a host whose DNS isn't pointed at it yet doesn't spend Let's Encrypt's failed-validation limit. The issuance stops nginx inside the same run, after the preflight passes, so a refusal never leaves nginx stopped, and the stop runs only once the names the request covers have passed. The preflight reads the target's resolver, not the CA's: see CertbotDnsPreflightOptions.expected_addresses for what that can't know.

Renewal scheduling also differs by distro: Debian's certbot package installs certbot.timer automatically; Alpine has none, so recipe_alpine_certbot.ts supplies alpine_certbot_renew_cron.

Neither schedule reloads anything after a renewal, so a server keeps serving the old certificate until it restarts. certbot_deploy_hook_core builds the file that closes that gap: an executable in CERTBOT_DEPLOY_HOOKS_DIR, which certbot runs after every certificate it renews, whatever started the renewal. The distro wrappers (debian_certbot_reload_nginx_hook, alpine_certbot_reload_nginx_hook) pass the reload command.

The caller passes the certificate's domain, the registration email, and the expected_addresses, each written out or a reference (zap.env('DEPLOY_DOMAIN')), which stays inert in the plan and is resolved by zap at apply time. Every value is one single-quoted word of the command (single_quote), so a value — a reference's or a literal — can't change what the command runs. Both requests pass --non-interactive --agree-tos: running either script agrees, for email, to the ACME server's terms (Let's Encrypt's subscriber agreement) without asking.

Recipes are imported at config eval time inside zap's sandboxed config eval (fgro eval), which has no network, no writes, and no environment, and where the clock and randomness throw. This module is therefore a set of pure functions: each only assembles strings from its arguments — no I/O, no clock, no randomness, and no import beyond types, single_quote and validate_run_parts_name, themselves pure. The output is deterministic for given inputs, so it stays a reliable content-addressed plan artifact.

The caller spreads each script result into a script resource, e.g. zap.script({id: 'ssl-certificate', name: '...', ...debian_certbot_standalone_issue({domain, email, expected_addresses}), depends_on: [...]}) with domain: zap.env('DEPLOY_DOMAIN'), email: zap.env('DEPLOY_CERTBOT_EMAIL') and expected_addresses: [zap.env('DEPLOY_HOST')], and a deploy hook into a file, e.g. zap.file({id: 'certbot-deploy-hook', name: '...', ...hook, depends_on: ['certbot']}) with const hook = debian_certbot_reload_nginx_hook(), which the webroot switch also takes (certbot_webroot_switch({domain, email, expected_addresses, deploy_hook: hook}), its script depending on the hook's file).

Build the path / mode / content of a certbot deploy hook, ready to spread into a zap.file({...}): an executable #!/bin/sh script at CERTBOT_DEPLOY_HOOKS_DIR/<name> that execs command.

A hook file rather than a --deploy-hook flag, so the renewal schedule (certbot.timer, a cron job) needs no arguments and any renewal, scheduled or run by hand, picks it up. On a certbot that also runs deploy hooks after certonly, the hook fires during the first --standalone issuance, while nginx is stopped, so command must succeed as a no-op when the service isn't running; the distro wrappers' commands do. A failing hook is reported by certbot but doesn't undo the renewal.

CertbotDnsPreflightOptions
#

recipe_certbot.ts view source

CertbotDnsPreflightOptions import type {CertbotDnsPreflightOptions} from '@fuzdev/zap/recipe_certbot.js';

The DNS preflight's option, shared by every certbot script that leads to a CA request.

expected_addresses

The IP addresses every name the certificate covers must resolve to, on the target. Before the script changes anything, the target resolves each name with getent ahosts and getent hosts — through its own resolver, so /etc/hosts first — and refuses when a name doesn't resolve, when no address can be read, or when any A/AAAA address either prints is outside this set: Let's Encrypt validates whichever address it picks, so an undeclared AAAA would fail the validation. The two lookups together see every A and AAAA but in one case: on a musl host (Alpine) with IPv6 disabled, ahosts drops the AAAA records and hosts prints only the first, so a name with several AAAA, the first of them declared, passes unseen.

The guard reads the target's resolver, not the CA's. An /etc/hosts line, a split-horizon answer, or a cached one can pass while public DNS doesn't point at the host yet, or refuse while it does. A name /etc/hosts maps to a loopback address refuses, the safe direction. That includes the 127.0.1.1 <name> line a Debian install writes for the host's own name, when that name is the domain: remove the line, or give the host a name that isn't the domain (a tool that manages /etc/hosts may write the line back).

Each value is an IP literal, or a reference resolving to one at apply time; the target checks it and refuses anything else (a host name, say), asking for this option. An IPv6 address is compared as text, lowercased, so write it as getent prints it (the compressed form). A reference to the target's host ([zap.env('DEPLOY_HOST')]) serves when that is an IP literal; list the addresses when the host is reached by name or the names also carry an AAAA. Required, and not empty.

type readonly string[]

The ACME challenge webroot. Defaults to /var/www/certbot.

type string

The deploy hook the run executes after certonly succeeds — the file a *_certbot_reload_nginx_hook returns, or any with its path — so the server loads the re-issued certificate: certbot before 5.3.0 runs deploy hooks for renew only.
