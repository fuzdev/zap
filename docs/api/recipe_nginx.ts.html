recipe_nginx.ts

The neutral nginx core shared by the recipe_debian_nginx / recipe_alpine_nginx wrappers.

These build the nginx config fragments for a single-page app behind nginx, SSL terminated by nginx, with an HTTP→HTTPS redirect. The site recipe assumes one app shape:

  • a static frontend in root (a prerendered SvelteKit build, say), its content-hashed assets under /_app, and a 200.html shell that client-side routes fall back to (spa_try_files changes the fallback chain);
  • a backend on a loopback port answering /api (HTTP and WebSocket), /health, and /ready, the readiness check a zap deploy health gate polls.

nginx rate-limits /api and /ready per client address, sets the security headers and CSP, and forwards the client's address in X-Forwarded-For. Everything else is the backend's: authentication, per-route limits (a login, say), refusing a credential where it shouldn't be used, and taking the client address from X-Forwarded-For only from the loopback hop. The fragments:

  • ssl_params — the shared ssl_protocols/ssl_ciphers/session snippet content, identical across distros, written at SSL_PARAMS_PATH on both.
  • rate_limit_zone — the limit_req_zone line for the http-context rate limiter, identical across distros.
  • nginx_site_core — the full site: the HTTPS server { listen 443 ssl } block (SSL, security headers, the /api proxy, /health, /ready, /_app, the SPA catch-all, plus any app-specific extra_locations) and the HTTP→HTTPS redirect server { listen 80 } block (ACME challenge + 301), plus an HTTPS redirect block when redirect_domains names aliases (www.). The wrapper supplies ssl_snippet_path — where the ssl: 'snippet' include points — which is SSL_PARAMS_PATH on both distros.

The server-block content and the snippet path are the same on both distros. What differs is placement: the caller writes the site to sites-available/ (linked into sites-enabled/) on Debian and to http.d/ on Alpine, and the rate_limit_zone file to conf.d/ or http.d/; and the stock default site sits in sites-enabled/ or http.d/. The public site recipes are the thin debian_nginx_spa_site / alpine_nginx_spa_site wrappers (with the matching *_nginx_catch_all) rather than this core.

Templating boundary

The site config is zap template content: the site recipes return the whole {type: 'template', template, vars, kinds} object, the caller's domain and port as its vars, so a caller writes zap.file({..., content: debian_nginx_spa_site({...})}) with domain: zap.env('DEPLOY_DOMAIN'), port: '4040', root, and csp. The body holds {{domain}} / {{port}} as placeholders, substituted at apply time once their references resolve, while eval-time values (the document root, the csp header value, …) are interpolated here.

{{domain}} lands in server_name, return 301 https://… and the certificate paths, and {{port}} in proxy_pass: a ;, { or } in either would end the directive or the block. The content declares them a hostname and a port, so zap refuses a value that is neither. Used whole, the content carries its kinds; overriding kinds or rebuilding the content drops them. A redirect_domains entry that carries a reference adds one more variable, redirect_domain_<i> (i its index in redirect_domains), held to hostname too. A literal redirect_domains entry is held to a host name when the recipe runs, whole labels of it {{domain}} where it uses the placeholder. Beyond those, a placeholder in extra_locations uses {{domain}} or {{port}}, and any other is a structural error when the config is read. The other values a caller gives (root, spa_try_files, …) are interpolated as text, so each is refused when it could end its directive or block.

Recipes are imported at config eval time inside zap's sandboxed config eval (fgro eval), which has no network, no writes, and no environment, and where the clock and randomness throw. This module is therefore a set of pure functions: each only assembles a string from its arguments — no I/O, no clock, no randomness, no imports beyond types and the pure single_quote, carries_reference, and letsencrypt_live_path. The output is deterministic for given inputs (stable ordering, trailing newline), so it stays a reliable content-addressed plan artifact.

The caller wraps each result in a file resource, e.g. for Debian zap.file({id: 'nginx-ssl-params', path: SSL_PARAMS_PATH, content: {type: 'inline', content: ssl_params()}}) (Alpine writes the same content at the same path).

The neutral core of the *_nginx_catch_all recipes: the stock-default removal at default_path and the catch-all server at catch_all_path.

The site recipes declare no default_server, so without a catch-all nginx answers a request for any other name (or none) with the first server on the port, the site, and the proxied locations forward that name to the backend as $host. The catch-all closes those requests instead. Order its file after the removal (the stock default site is itself a default_server, and two fail nginx -t, the file's validate) and after the SSL parameters it includes. A site meant to answer any host name declares only the removal.

nginx_site_core
#

recipe_nginx.ts view source

(options: NginxSiteCoreOptions): NginxSiteContent import {nginx_site_core} from '@fuzdev/zap/recipe_nginx.js';

Build the full nginx site config for a single-page app behind nginx — the neutral core the distro wrappers call.

Composes the HTTPS server block — SSL cert + the SSL params (snippet or certbot), HTTP/2 unless http2 is off, server_tokens off, an optional server-level client_max_body_size, the document root, the security-header set with hsts and the CSP (repeated in the /_app and location / blocks, which set headers of their own and so inherit none; the proxied locations inherit it), a rate-limited /api reverse proxy (with WebSocket upgrade headers + Authorization forward + timeouts), /health, the /ready readiness check (what a zap deploy health gate polls), the immutable /_app static block, any extra_locations, an optional error_page 404, and the SPA catch-all location / (no-cache + the try_files fallback) — plus the HTTP→HTTPS redirect server block (ACME challenge served plain, everything else 301'd), and, for any redirect_domains, an HTTPS server that 301s them to {{domain}}, sending the same HSTS header. The app shape it serves, and what it leaves to the backend, are in the module doc.

Neither server is a default_server: the *_nginx_catch_all recipes add one that gives a request for any other host name no answer, so the proxied locations forward only this site's names to the backend as $host.

{{domain}} / {{port}} are placeholders for zap's template engine, their values the options' domain and port; root/csp/etc. are interpolated from the options, each refused when it could change the config's structure. extra_locations is the exception: it is nginx config by design, spliced in as given. Prefer the debian_nginx_spa_site / alpine_nginx_spa_site wrappers, which supply ssl_snippet_path for you.

ssl?

How SSL is wired into the HTTPS server.

  • 'snippet' (default) — include <ssl_snippet_path>; (paired with the ssl_params recipe written to that path; zap owns the full config).
  • 'certbot' — include /etc/letsencrypt/options-ssl-nginx.conf; + ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem; (certbot-managed params).

type "snippet" | "certbot"

hsts?

The Strict-Transport-Security header every HTTPS server sends, the redirect server included. Defaults to {}: max-age a year, without includeSubDomains.

A browser that has seen the header refuses plain HTTP to the name until max-age runs out, and with include_subdomains to every name under it too, so a subdomain served over HTTP alone stops loading in that browser. Set include_subdomains only when every name under the domain serves HTTPS. A browser forgets the policy once it sees max_age: 0, the way to undo one; false sends no header, which forgets nothing.

type NginxHsts

http2?

Serve HTTP/2 in the HTTPS server. Defaults to true.

On by default because the alternative is a worse baseline for every site: without it a browser is capped at six connections per origin and repeats every request and response header uncompressed, which dominates the wire cost of any page serving many small assets. HPACK plus multiplexing removes both, and ALPN falls back to HTTP/1.1 for clients that can't negotiate h2, so there is no client-compatibility cost.

Emitted as the listen ... http2 parameter rather than the http2 on; directive. The directive is the modern spelling, but it only exists from nginx 1.25.1; on anything older it is an unknown directive that fails nginx -t outright, and Ubuntu 24.04 LTS ships nginx 1.24. The parameter form works on both sides of 1.25.1 (deprecated above it, still honored, one warning logged at start), so it is the spelling that delivers h2 on every supported host.

One thing to know before turning it off — and the reason this is an option at all rather than unconditional:

  • limit_req burst= absorbs arrival pattern, and h2 changes it. The /api burst was sized against requests trickling in six at a time; over one multiplexed connection a page's whole RPC fan-out can arrive at once. The zone rate is unaffected (limit_req counts requests, not connections), but a site with a heavy fan-out on load may need a larger api_burst than it did on HTTP/1.1.

type boolean

client_max_body_size?

Server-level client_max_body_size cap, a number with an optional k, m, or g ('4m'). Emitted as its own line (with the surrounding blank lines) only when set; omit for nginx's default.

type string

client_max_body_size_comment?

App-specific comment line rendered directly above client_max_body_size (without the leading # , which is added here). One line: a line break is refused, since the text after it would be read as config. Ignored unless client_max_body_size is set; omit for no comment.

type string

api_burst?

/api limit_req burst=, a whole number. Defaults to 50.

type number

spa_try_files?

The location / try_files arguments (the SPA fallback chain), words separated by spaces. Defaults to '$uri $uri/index.html /200.html'. A ;, {, }, a quote, #, \, a tab, a line break, or a NUL is refused.

type string

error_page_404?

error_page 404 <target>; in the HTTPS server, e.g. '/404.html', held to the rule spa_try_files is. Emitted only when set.

type string

extra_locations?

App-specific location blocks injected into the HTTPS server verbatim (already indented to the server-block level, no leading/trailing blank lines), placed just before the /_app static block. A block with no add_header inherits the server's security headers and CSP; one with its own inherits none, so it renders site_security_header_directives({csp, hsts}) beside them, or a Content-Security-Policy of its own. A block (a location, or an if in one) that sets add_header with no Content-Security-Policy is refused.

type string

acme_webroot?

ACME HTTP-01 challenge webroot for the redirect server, one word as root is. Defaults to /var/www/certbot.

type string

redirect_domains?

Further host names that 301 to https://{{domain}} — e.g. ['www.{{domain}}'] to send www. to the apex. Each joins the HTTP server's server_name (so the ACME challenge is served for it too) and gets a lean HTTPS server that only redirects, on the site's certificate, so the cert must cover them: pass the same names to the certbot recipes' extra_domains. Defaults to none.

A literal name is a host name, held to the hostname kind's form when the recipe runs, where whole labels may be the {{domain}} placeholder, substituted with the rest of the template; any other placeholder is refused. A name that carries a reference (zap.env('MIRROR_DOMAIN'), whole or interpolated) becomes its own variable, redirect_domain_<i> for the entry at index i, held to hostname once it resolves; it takes no placeholder, since a variable's value is never read for one.

type readonly string[]

RATE_LIMIT_ZONE
#

recipe_nginx.ts view source

"global" import {RATE_LIMIT_ZONE} from '@fuzdev/zap/recipe_nginx.js';

The single rate-limit zone name, shared by rate_limit_zone (which defines the zone) and nginx_site_core (whose /api + /ready limit_req directives reference it). One constant so the definition and the references can't drift — a limit_req naming a zone no limit_req_zone defined fails nginx -t. (This is why the zone name isn't an option: it would let the two sides diverge silently.)

A fixed name assumes one zap-managed site per host. Two of them would write the same rate_limit.conf path with each other's rate — fighting on every apply — and co-declaring the zone in one http context fails nginx -t on the duplicate. Co-hosting needs a per-site zone name (and path) before it needs anything else here.

Exported so a config's own limit_req (in an extra_locations block) references the zone by this constant rather than repeating its name.

The on-disk path of the ssl_params snippet, the same on Debian and Alpine: the distro site wrappers pass it as ssl_snippet_path, and a config writes the ssl_params file here. Under snippets/, never Alpine's auto-included http.d/, which would declare the session zone a second time.

SslParamsOptions import type {SslParamsOptions} from '@fuzdev/zap/recipe_nginx.js';

Options for ssl_params.

session_cache_zone?

The ssl_session_cache shared-memory zone's name: letters, digits, and _. Defaults to 'zap_SSL'. Renaming it on a running host allocates a new zone at the next reload, dropping the cached sessions.

type string
